## 如何解读

C 的小型雕塑与真实内容主导布局，在此环境的滚动间隔明显优于 A/B 的大型画布。A/B 的 P95 多次超过50ms，不能称为已经达到高级动效应有的流畅度。B 桌面混合序列的布局移动累计值还高于0.1目标；其top/left/width/height式展开编排没有通过原先的布局稳定预算。C 在4×CPU下也出现退化，仍需真实移动GPU验证。

A 复用LivingGallery，保留可靠交互的同时加载原组件与媒体；B 的多层透视和大画布增加工作量；C 的原始项目图像也有传输成本。应按这些实际成本选择下一轮方向，不能用动画数量或着色器行数替代判断。

解码JS是浏览器实际获取的脚本体积，子资源传输不含HTML主文档，含本地服务器协议开销；不是新增依赖的gzip总量。初版计划的增量gzip预算尚未通过bundle归因证实。当前没有新增框架/包依赖，只有一个运行命令；不能把这一点等同于零性能增量。

已实施的工程取舍：4304三角形静态闭合网格、程序化光照，无外部纹理；像素面积上限42万、DPR上限1.25；ResizeObserver缓存未变换尺寸，避免每帧按CSS变换重新分配画布；数值状态与DOM写入不通过每帧React state；静止停止绘制、离屏/隐藏暂停、切换销毁context。

原始48次：[performance.json](evidence/performance.json)。完整录屏矩阵中的metrics另受视频编码与交互时长影响，只作为描述记录，不用于此表的相对结论。

原始JSON中的 `lcpMs` 是整段观察的末次候选，可能在程序化滚动扩大主图时继续更新，**不能当作初始加载LCP**；因此不把它放入首屏性能比较表，也不据此推断C首屏比A/B慢。表中CLS同样覆盖程序驱动的运动序列，不能直接当成真实用户CWV。后续集成前需用真实输入的导航/滚动及现场测量补齐加载评估。
